# Collie Barkup backup service v1

Collie Barkup is a standalone Rust service for receiving and restoring encrypted archive bytes. It does not interpret `main` or metadata. It validates the local archive `files` manifest so media references remain intact.

## Storage

`SignalBackups/signal-backup-<UTC timestamp>/{metadata,main,files}` stores finalized snapshots. The timestamp exactly follows Android's `yyyy-MM-dd-HH-mm-ss` UTC pattern; clients must send UTC timestamps, not local time. Media live at `SignalBackups/files/<first two lowercase hex>/<64 lowercase hex SHA-256 media name>`. Upload data stays in `.uploads/`; a snapshot candidate is `SignalBackups/signal-backup-<timestamp>-tmp`. Members are staged there and published as one directory by same-filesystem rename only after validation. The newest `BARKUP_RETENTION` snapshots remain (default 2). Retention removes older snapshots from the published namespace before removing their contents. Signal derives the media name from its plaintext hash and local backup key. The service preserves the encrypted bytes under that name and never overwrites existing media.

The `files` member is a sequence of protobuf length-delimited `FilesFrame` messages. `mediaName` is string field 1. Every frame must be well-formed and contain exactly one valid mediaName. Unknown fields and unsupported encodings fail closed so an unrecognized frame cannot hide a media reference. Bytes are stored unchanged.

## HTTP API

Readiness: `GET /health` is unauthenticated and returns only `{"ready":true}`. The listener defaults to `127.0.0.1:18082`; set `BARKUP_BIND=0.0.0.0:8082` in a container.

All `/v1` routes except `POST /v1/pair/redeem` require `Authorization: Bearer …`. Credentials in query strings are rejected with `400`; absent credentials return `401`; invalid or revoked credentials return `403`. Authenticated responses use `Cache-Control: no-store`.

- `GET /v1/files` returns `200` and `{"files":{"<name>":<bytes>}}`.
- `PUT` and range-capable `GET /v1/files/<shard>/<name>` transfer finalized media. PUT returns `201` for new media, `200` for identical existing content, and `409` for different existing content. Downloads stream from the opened file; successful responses include `Content-Length` and `Accept-Ranges: bytes`. A valid single byte range returns `206` and `Content-Range`; an invalid or unsatisfiable range returns `416` and `Content-Range: bytes */<length>`.
- `POST /v1/uploads` takes `{"name":...,"length":...}` and returns `201` with an upload ID. `PATCH /v1/uploads/<id>` takes `Upload-Offset` and a non-empty body of at most 32 MiB. A `204` response acknowledges only bytes flushed and synced to disk, with the new offset in `Upload-Offset`; `HEAD /v1/uploads/<id>` returns `204` and the committed offset. On disconnect, retry HEAD and resume at the returned offset. Upload sessions survive daemon restart. Sessions idle for seven days are cleared at startup and during subsequent writes or pruning. `POST /v1/uploads/<id>/commit` returns `201` after publishing and `200` for identical media already present. If a process stops between publishing the bytes and completing the upload session, repeating the commit verifies the saved digest and completes the session with `200`. If a media commit response is lost and the session is already gone, fetch `GET /v1/files/<shard>/<name>` and verify the downloaded bytes against the original upload; a successful commit removes the upload session.
- `POST /v1/snapshots/<timestamp>` begins a stage with `201`; `PUT /v1/snapshots/<timestamp>/{metadata,main,files}` writes exact member bytes up to the request limit and returns `204`. For larger members, `POST /v1/snapshots/<timestamp>/uploads/{metadata,main,files}` with `{"length":N}` creates a resumable upload with `201`. Send bounded `PATCH /v1/uploads/<id>` chunks and commit with `POST /v1/uploads/<id>/commit` before finalizing. The `files` manifest is parsed frame by frame from disk during upload commit and snapshot finalize. `POST /v1/snapshots/<timestamp>/finalize` validates references and atomically publishes: it returns `201` on first publication and `200` when a retry confirms the already-published snapshot. A `409` means the timestamp has an active member upload or no usable published snapshot. A stage with missing or invalid members returns `422`. `GET /v1/snapshots` returns `200` and lists newest first; `GET /v1/snapshots/<timestamp>/{metadata,main,files}` streams members and supports the same byte range headers. After an uncertain finalize response, check `GET /v1/snapshots` and fetch the members to verify them; finalized snapshots are immutable and cannot be staged again under the same timestamp.
- `POST /v1/files/prune` returns `200` with `removed_bytes` after deleting unreferenced media, and returns `409` while uploads or snapshot stages exist. Finish active work or let idle uploads and snapshot stages expire before pruning. Pruning clears stages idle for seven days unless they have a live upload.
- `POST /v1/pair/redeem` accepts `{"token":"…","label":"optional device label"}` once and returns `200` with the `pairing.schema.json` version 1 device credentials and sanitized label. Invalid labels or payloads return `400`; expired and replayed tokens return `403`. Labels are limited to 64 ASCII letters, digits, spaces, dots, underscores, and hyphens. `collie-barkup pair create --url https://backup.example` (or `BARKUP_URL`) emits exactly the bootstrap schema (`collie_barkup_pairing: 1`, `url`, `token`, RFC3339 `expires_at`); the bootstrap token expires at the displayed time, 10 minutes after creation. There is no default pairing URL. Run `collie-barkup devices list` and `collie-barkup devices revoke <id>` to inspect or revoke devices. In the image, invoke CLI commands directly (for example `docker run --rm -v barkup-data:/data IMAGE pair create --url https://backup.example`); the default command is `serve`.

## Configuration and limits

`BARKUP_DATA` defaults to `/data`; `BARKUP_STATE_DIR` optionally places auth state separately and defaults to the data directory. `BARKUP_TOKEN` or `BARKUP_TOKEN_FILE` enables static bearer authentication. Device and bootstrap state is stored as SHA-256 token hashes in a mode 0600 file under the operator's private state directory. Corrupt state fails closed. The server holds a nonblocking lock on its data directory so only one serving process can mutate it. `BARKUP_MAX_BYTES` (default 100 GiB) must be a nonnegative integer. It accounts for committed files and unfinished upload reservations, including 4 KiB per upload for durable state. `BARKUP_RETENTION` controls snapshot count. This service stores and restores encrypted archive bytes; it does not decrypt, interpret, or migrate Android backup contents.

Run `python3 conformance/check.py` for canonical fixtures and `BARKUP_BIN=target/debug/collie-barkup bash conformance/run.sh` for live loopback schema and status checks. Integration tests launch the binary and exercise the real HTTP listener.

The service bounds request bodies to 34 MiB and chunks to 32 MiB, enabling files larger than 100 MB to transfer in chunks. Filesystem routes reject invalid names and symlink targets. Use a private writable data directory.
